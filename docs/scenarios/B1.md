# Scenario B1: owner-level default dedupe (brownfield enhancement)

Branch: `feat/b1-owner-dedupe-default` (from `main`; not merged)

## Ticket
URL-SCN-B1 / URL-FR-1.4 / PRD A4: add an owner-level default for dedupe. A request's `dedupe`
field, when present, overrides it. Includes a DB migration (design §11.3).

## AI interaction summary
- The AI drafted `V2__owner_dedupe_default.sql`, copied verbatim from design §11.3 (the human
  pre-approved this migration for this branch only).
- `CreateLinkRequest.dedupe` changed from `boolean` to `Boolean`; `null` means "use the owner
  default".
- `LinkService` resolves `effectiveDedupe = request != null ? request : owners.dedupe_default`.
  Dedupe is still ignored when an alias is given (design §3.3).
- The owner default is read through a new `LinkRepository.ownerDedupeDefault(ownerId)` query
  rather than a new constructor dependency, so existing tests keep their wiring. It is only
  queried when the request omits `dedupe` and has no alias.
- Decision for review: the default is read per request (not cached with the API key), so a
  change takes effect immediately.

## Migration notes (design §10.5 evidence)
- Backward-compatible: `ADD COLUMN ... NOT NULL DEFAULT FALSE` is a metadata-only change in
  PG 11+ (no table rewrite, short `ACCESS EXCLUSIVE` lock only). Existing owners get `false`,
  which is the previous behaviour.
- Tested on a copy of the seed: `SeedDataIT` applies V1, V1_1 (demo seed) and V2 under the
  `local` profile; the seed invariants still hold. `OwnerDedupeDefaultIT` checks the column
  definition (`boolean`, NOT NULL, default false).
- Rollback / forward fix: the app ignores the column when every request sends `dedupe`; to
  roll back the code, deploy main (it never reads the column). Dropping the column
  (`ALTER TABLE owners DROP COLUMN dedupe_default`) is a later, separately approved contract
  step (expand -> migrate -> contract).
